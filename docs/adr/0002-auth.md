# ADR 0002: Accounts, sessions and roles

Status: accepted.

The original demo had Manus OAuth and no sign-in screen. A clinical system needs individual accounts and an audit trail of who did what.

- **Passwords:** Argon2id (the `argon2` package), minimum 10 characters with a letter and a number. No composition theatre beyond that.
- **Sessions:** a random token in an HttpOnly, SameSite=Lax cookie (Secure when served over HTTPS). Only a SHA-256 hash of the token is stored. Sessions last 12 hours and are deleted when a user is deactivated, changes role, or gets a new password.
- **CSRF:** every write must carry a header that only our own client sends. Cross-site forms cannot set it.
- **Brute force:** five failed sign-ins lock the account for 15 minutes (and are audited); sign-in is also limited to 10 attempts per 15 minutes per address and email. The limiter is in memory, which is right for one API process; with several, move it to the database.
- **No account enumeration:** a wrong password and an unknown email give the same answer.
- **Roles:** Admin, Inventory manager, Pharmacist, Vet, Viewer; one role per user; the map is in `shared/permissions.ts`, enforced on the server, mirrored in the interface only to hide buttons.
- **Forgotten passwords:** there is no mail server, so email reset is **not offered as working**. The API says so, creates no token, and tells people to ask their admin, who sets a new password in Settings. A locked-out admin is recovered from the server with `pnpm user:set-password`. If a mailer is added later, it plugs into `resetDelivery` in `server/app.ts` and the existing token flow (hashed, one hour, single use) takes over.
- **Why not an identity provider:** a single-sign-on integration adds an external dependency and a vendor decision the clinic has not made. The session code is small enough to replace when they do.
- **Why sessions and not JWTs:** sessions can be revoked instantly, which matters when someone leaves.
